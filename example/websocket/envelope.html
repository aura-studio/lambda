lambda / tunnelkit · 设计注解

信封The Envelope — {"meta":{…}, "data":"…"}

它不是 AWS 的要求，也不出现在任何 Lambda 文档里。 它是 Invoke(string, string) string 这个签名的必然产物： 当一根 string 既要运结构、又要运二进制、还要运元信息时，你必须自己造一个信封。

"meta": { … } ← 旁路 "data": "base64…" ← 载荷
SCROLL ▾
01

先分清三层格式

讨论"信封是不是必须的"之前，先看清它在哪一层。三层里只有第一层出自 AWS 之手。

①

AWS 强制格式

API Gateway ↔ Lambda

APIGatewayWebsocketProxyRequest 进，APIGatewayProxyResponse{statusCode} 出。这是唯一由 AWS 定义、不可协商的部分。信封不在这层。

②

框架内部约定

engine ↔ tunnel · 信封在此

引擎把请求装进 {"meta","data":base64} 交给 tunnel.Invoke，返回时再拆包。AWS 永远看不到它——它止步于进程内部。

③

应用自定义协议

client ↔ API Gateway

客户端看到的 {"path","payload"} / {"path","error"}，是引擎拆箱后重新组装的。改它只需改引擎的回包函数，与信封无关。

02

一个数据包的旅程

跟着 {"hello":"world"} 走完全程。点击节点跳步，点击报文里黄色的 base64 可以解码/装回。

03

为什么必须有它

四条各自独立的约束，收敛出同一个解。删掉信封，等于同时推翻这四条。

∴根源：单字符串通道

dynamic.Tunnel 的签名是 Invoke(string, string) string——进出各只有一根 string。要在这根 string 里同时塞进"结构化的寻址 + 任意字节的载荷 + 旁路元信息"，除了自编码一个信封，别无选择。这不是审美决策，是类型系统的硬约束。

⇄meta：不污染载荷的旁路

HTTP 引擎要给响应标 ContentType/Status，调用链要传 traceId——这些信息属于"运输"，不属于"货物"。meta 之于 data，正如 HTTP headers 之于 body。

␍base64：二进制过文本桥

JSON 字符串无法安全承载任意字节（控制字符、非法 UTF-8 都会炸）。载荷可能是 protobuf、图片、压缩包——base64 用 33% 的体积换"任何字节都能活着过桥"。

≠meta.Error：两种失败的分离

"系统坏了"（引擎 panic → 500）和"业务拒绝"（余额不足 → meta.Error）是性质完全不同的失败。信封让业务错误搭乘正常响应回家，调用方得以区分 retry 还是放弃。

×3兼容性红利：一个 tunnel，三个引擎

信封是稳定契约：http / sqs / websocket 三个引擎说同一种"信封语"，于是 slots 现成的 tunnel 零改动就被 WebSocket 复用。契约越稳定，生态越敢生长。

04

它站在哪些肩膀上

信封没有发明任何新东西——它只是把几个久经考验的模式，缩进了进程内的一根 string 里。

RFC 9110
HTTP headers / body

元信息与载荷分离的祖师爷。header 改名不影响 body，body 换编码不影响 header。

借来 → meta 与 data 的分层
gRPC
metadata + message framing

gRPC 的 metadata（键值对）与二进制 message 分帧传输，错误状态走 trailer 而非消息体。

借来 → 错误不走载荷通道
JSON-RPC 2.0
method / params / error

单通道 RPC 的经典信封：{"method","params"} 调用，{"error"} 与 {"result"} 互斥返回。

借来 → path/payload 与 error 的形状
RFC 2045 · MIME
Base64

1996 年为了让二进制附件穿过只认 7-bit 文本的邮件系统而生。同样的桥，同样的船。

借来 → data 字段的编码方式
AWS 自家
body + isBase64Encoded

API Gateway 代理事件里，AWS 自己就用一模一样的招：JSON 事件塞二进制 body，配一个 isBase64Encoded 标记。

佐证 → 同问题，同解
本仓旁证
sqs protobuf Request

同仓库 sqs 引擎用 protobuf 定义 Request{path, payload, correlation_id}——序列化方式不同，信封思想相同。

佐证 → 与序列化无关的必然

信封是框架内部的运输箱。
客户端收到的是拆箱后的货物，不是箱子。
